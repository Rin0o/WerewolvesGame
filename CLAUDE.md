# Werewolves of Miller's Hollow — Claude Context

## Project Overview
A React Native (Expo) mobile app for the social deduction game "The Werewolves of Miller's Hollow". All game logic runs client-side, coordinated through one Firestore document per room. No backend server. Current version: **1.0.0** (Android). User-facing documentation lives in `README.md`; this file is the developer/AI context and should stay consistent with it.

## Tech Stack
- **Expo ~57** (React Native 0.86, React 19.2) — New Architecture only
- **Firebase 10** — Firestore (real-time game state) + Anonymous Auth (UID persisted via AsyncStorage, so it survives app restarts)
- **React Navigation 7** — Native Stack (`createNativeStackNavigator`). In v7 `navigate()` never goes back to a screen already in the stack (it pushes a new one); every Leave button uses `navigation.popTo('Home')`
- **react-native-reanimated 4** — PhaseTransition animation
- **expo-audio** — sound effects (`useSoundEffect`); replaced `expo-av`, which was removed in SDK 55
- **AsyncStorage** — the player profile (name + sound setting, `utils/profile.js`), per-player notes/suspicions (`usePlayer`) and the active-game session for Rejoin (`utils/session.js`)
- **expo-constants** — reads the app version from `app.json` for the settings panel
- **qrcode** (JS only, `qrcode/lib/core/qrcode`) — builds the lobby QR matrix, drawn with plain Views (no react-native-svg)
- **expo-camera** — QR scanner on Home (`CameraView` with `barcodeTypes: ['qr']`); plugin in `app.json` with camera permission only (`recordAudioAndroid: false`)
- `android/` is committed and generated by `npx expo prebuild --platform android` (clears and regenerates by default). Native config belongs in `app.json` or a config plugin in `plugins/`, never hand-edited in `android/`.

## Firestore Data Structure

### `rooms/{roomId}`
```
{
  code: string                    // 5-char uppercase join code
  hostId: string                  // Firebase Auth UID of host (changes on host takeover)
  hostHeartbeat: number           // Incremented by the host every 8s; others detect a stale host from it
  memberIds: string[]             // Real players' UIDs (no bots); set on create, arrayUnion on join, arrayRemove
                                  // on lobby leave. Used only by firestore.rules for membership checks
  status: "lobby"|"night"|"day"|"ended"
  phase: number                   // Cycle count (0 in lobby, 1 on the first night, +1 each night)
  phaseStartedAt: ISO string      // Client-side timer sync reference
  createdAt: Timestamp
  players: [                      // Array of player objects, in join order (= Bear Tamer seating)
    { id, nickname, isAlive, isHost, isReady, isBot?, isNarrator? }
  ]
  roles: { [playerId]: role }     // NEVER render other players' roles (except GameOver / narrator)
  nightSubPhase: "thief"|"cupid"|"werewolf"|"witch"|"seer"|"saviour"|"done"
  nightActions: {
    werewolf: playerId            // Who wolves picked to kill (night 2+)
    werewolfObserved: true        // Night 1: wolves have seen each other (no kill)
    seer: playerId                // Who seer inspected
    witchSave: playerId           // Who witch saved (equals werewolf target if used)
    witchPoison: playerId         // Who witch poisoned
    witchSkip: true               // Witch chose no action
    saviour: playerId             // Who the saviour protected
    cupid: [playerId, playerId]   // Two lovers chosen (phase 1 only)
    thief: role                   // Role the thief stole (phase 1 only)
  }
  witchPotions: { [playerId]: { save: bool, poison: bool } }
  saviourLastProtected: playerId|null  // Can't be protected again the next night
  eliminatedThisNight: playerId[]|null  // Everyone who died last night (incl. lovers' heartbreak)
  nightDeathCauses: { [playerId]: "werewolves"|"poison"|"heartbreak"|"abandoned" }
                                  // Why each player died last night; drives the "You were eliminated" message
  bearTamerGrowl: bool|null       // Set at dawn: true if a living neighbour of the Bear Tamer is a wolf; null if no Bear Tamer alive
  events: string[]                // Append-only game event log (written with arrayUnion)
  votes: { [voterId]: { target: playerId, confirmed: true } }
  votesClosed: bool               // Set by timer expiry (host) or the narrator's Close Votes
  winner: "villagers"|"werewolves"|"lovers"|null
  hunterTriggered: playerId|null  // Set when Hunter dies, cleared after shot
  hunterDiedDuring: "night"|"day"|null  // When the Hunter died; after the shot only "day" ends the day (next night)
  lovers: [playerId, playerId]|null  // Set by Cupid on night 1
  disconnectedPlayers: string[]   // Players who clicked Leave; cleared at phase end
  gameMode: "normal"|"custom"|"narrator"  // Set by host in lobby; defaults to "normal" if absent
  customRoles: {                  // Only used when gameMode === "custom"
    playerCount: number           // Target total players (must equal effectiveCount to start)
    werewolf: number              // Count (min 1)
    seer, witch, hunter, cupid, thief, saviour, bear_tamer: boolean
    sister: boolean               // When true, adds 2 Sister slots (counted as 2 in usedSlots)
    // villagers = playerCount − werewolf − sum(enabled specials); auto-filled
  }
}
```

### Win Conditions (`checkWinCondition`, narrator excluded)
- **Lovers win**: the two lovers are the last two players alive (checked first; overrides team allegiance)
- **Villagers win**: no living werewolves
- **Werewolves win**: living werewolves ≥ all other living players
- While `hunterTriggered` is set, `resolveNight`/`resolveLynch` skip the win check; `hunterShoot()` checks after the shot

### Night Order (`computeNightSequence`)
- **Night 1**: Thief (if alive and roles are available) → Cupid → Werewolves (observe only: `werewolfObserved`, no kill). The Seer does not wake on night 1.
- **Night 2+**: Saviour → Werewolves (pick victim) → Witch (only if she has a potion left) → Seer
- Roles that are absent, dead or disconnected are skipped (`FIRST_NIGHT_ORDER` / `LATER_NIGHT_ORDER` filtered by who can act). The host advances `nightSubPhase` with `nextNightSubPhase(room, current)` — the next step in the full order that still has someone to act — when `isSubPhaseDone()` is true **or** the current step's player has left (`disconnectedPlayers`), and calls `resolveNight()` after the last step. Never compute "next" from the index in `computeNightSequence()`: a step whose player left is no longer in that list.
- `resolveNight` order: Thief swap → Saviour block → Witch save → wolf kill (+ lover chain) → Witch poison (+ lover chain) → disconnected players (+ lover chain) → Hunter trigger / win check → Bear Tamer growl. Wolves and Witch poison do nothing on night 1.

### Role Details

**Werewolf** — from night 2, the wolves pick a victim together (any wolf's submission counts). They coordinate in the wolf chat, available at night and during the day. On night 1 they only see each other (`werewolfObserved`).

**Seer** — from night 2 on, each night selects a player and sees whether they are a Werewolf. The result is shown locally and the seer must dismiss it before the day phase begins (navigation deferred via `pendingDay` ref).

**Witch** — has one Save potion (revive that night's victim) and one Poison potion (kill any player). Each potion can only be used once per game. One choice per night: save OR poison OR skip. Not woken on night 1, nor once both potions are used.

**Hunter** — when eliminated (night or day), `hunterTriggered` is set to their playerId. Their day screen shows `HunterSection` with a 20s timer (random target on expiry). `hunterShoot()` eliminates the target (+ lover chain) and re-checks the win condition. If there is no winner, what happens next depends on `hunterDiedDuring`: after a day lynch (`'day'`) the host calls `startNextNight(roomId)` — it reads the room fresh from Firestore (so the night is planned without the player just shot) and only acts while `status === 'day'` with no winner and no pending shot; after a night death (`'night'`) the day simply continues with discussion and voting.

**Cupid** — on night 1 only, chooses exactly 2 players to become lovers. Lovers are stored in `room.lovers`. If one lover dies, the other immediately dies of heartbreak. If the two lovers are the last alive, they win together regardless of team.

**Thief** — on night 1 only, chooses one of the roles nobody was dealt, from `ALL_SELECTABLE_ROLES` (villager, werewolf, seer, witch, hunter, cupid — `getAvailableRolesForThief`). The swap is applied in `resolveNight` and recorded silently in the event log ("A shadowy figure stole a role in the dark."). If no roles are available, the Thief step is skipped and the Thief sides with the villagers.

**Saviour** — from night 2, protects one other player (not themself) from the wolves. Can't pick `saviourLastProtected` (shown greyed out). Protection blocks only the wolf kill, not the Witch's poison.

**Bear Tamer** — no action. At dawn `computeBearTamerGrowl()` checks the Bear Tamer's two neighbours among *living* players in `players` (join) order, wrapping around. If either is a werewolf, `bearTamerGrowl = true` and `NightAnnouncement` shows "The bears growled at dawn." to everyone.

**Sisters** — two players who know each other's identity at game start. No night action. Their role key is `sister` (each gets the same key); `getSisters(roleMap)` returns both IDs. `useGameState` exposes `gs.isSister` and `gs.fellowSisters` (the other sister's ID). At `RoleRevealScreen`, the RoleCard shows a "Your Sister" box identical in structure to the wolves' "Fellow Werewolves" box. The custom-mode lobby toggle adds 2 slots (handled by `usedSlots` reduce counting `sister` as 2).

### Lover Chain
`eliminateWithLoverChain()` in gameManager.js handles lover death propagation. When any player is eliminated, their lover (if alive) is also eliminated immediately. This applies to wolf kills, witch poison, lynch, hunter shot, and disconnected players.

## Key Conventions
- **Roles are private**: `roles` map written by host on game start. Clients read `roles[myPlayerId]`. Never render other players' roles except on GameOver, a lynched player's reveal, dead players in the day list, and the narrator's dashboards.
- **Host is orchestrator**: Host client detects when all night actions are in and calls `resolveNight()`. On day phase, host closes voting on timer expiry and calls `resolveLynch()` after the result screen. Disconnected players are skipped in both checks. Every host-only effect lists `gs.isHost` in its deps so a player who becomes host mid-phase picks up the work.
- **Host failover**: `useHostFailover(roomId, playerId, room)` runs on Lobby, RoleReveal, Night, Day and GameOver. The host increments `hostHeartbeat` every 8s. Other clients time how long since they last *saw* it change (local clock, so no device clock skew). After 25s the next candidate in `players` order (non-bot, non-narrator, not disconnected) takes over via a Firestore transaction (`takeOverHost`) that only succeeds if `hostId` and `hostHeartbeat` are unchanged; each further candidate waits 6s more. Disabled in narrator games once started (only the narrator can drive). Screens remember if a phase timer already expired (`subPhaseTimerExpiredRef`, `discussionTimerExpiredRef`) so a new host catches up immediately. `Timer` and `LynchResultModal` call the latest `onExpire` via a ref, never a stale closure.
- **Rejoin after closing the app**: `LobbyScreen` saves `{ roomId, playerId, nickname }` via `utils/session.js`; every Leave button clears it. `HomeScreen` checks the saved session on mount/focus (same Firebase anon UID, room exists, player still listed) and shows a Rejoin card that navigates to the screen for the current `status` (`screenForStatus`). Rejoin and join-by-code call `forgetRoomSnapshot()` first so a stale cached status can't trigger navigation.
- **One vote per day**: Each living player votes for one target (`votes[voterId] = { target, confirmed: true }`). Voting ends when all eligible players have voted (`allVotesIn`) or `votesClosed` is set (discussion timer / narrator). `tallyVotes`: the single top target is lynched (+ lover chain); a tie or no votes eliminates nobody. Unless there's a winner or a Hunter shot pending, `resolveLynch()` always moves to `status: 'night'` and increments the phase.
- **Vote feedback**: DayPhaseScreen snapshots the vote map into local `lastLynchResult` state the moment voting ends — before `resolveLynch` wipes `votes: {}`. `LynchResultModal` shows it (verdict, tally, per-player votes, role reveal if lynched) for 8s; on expiry the host calls `resolveLynch()`.
- **Events are atomic**: All game events are written using Firestore `arrayUnion(...events)` inside the same `updateRoom()` call that changes `status`. Never use separate `addEvent()` calls from game logic — this caused race conditions where clients saw the status change before events landed.
- **Game start**: `startGame()` writes roles + `status: 'night'` immediately and clears the old wolf chat in parallel (don't block the start write on cleanup). The Lobby's Start button shows "Starting..." and ignores double taps.
- **Back navigation blocked**: NightPhaseScreen and DayPhaseScreen block the Android hardware back button (`BackHandler`) and iOS swipe-back gesture (`navigation.setOptions({ gestureEnabled: false })`). Players exit via an explicit "Leave" button that shows a confirmation dialog. Day: bottom bar (`leave.webp`). Night: bottom bar (`exit_game.webp`). Both call `disconnectPlayer()` + `clearSession()` and go to Home.
- **Player disconnection**: On confirmed exit, `disconnectPlayer()` adds the player to `disconnectedPlayers` (arrayUnion). On screen focus, `reconnectPlayer()` removes them (arrayRemove). At each phase end (`resolveNight`, `resolveLynch`), disconnected alive players are eliminated and `disconnectedPlayers` is cleared atomically.
- **Bot support**: `devConfig.js` exports `BOT_CONFIG { enabled, bots: [{ nickname }] }` (currently `enabled: false`). When enabled, bots are injected at game start. The host auto-submits bot night kills and day votes. Roles are random every game: the composition is shuffled, bots take random `werewolf`/`villager` slots (they can't play special roles), and humans get the rest, so a human can be a wolf even with bots on.
- **Game modes**: Host selects Normal, Custom, or Narrator in the lobby (`room.gameMode`). Normal uses preset `ROLE_COMPOSITIONS` tables. Custom uses `buildCustomComposition(room.customRoles)` — host configures player count, werewolf count, and special role toggles; villagers auto-fill the remainder. `startGame()` accepts an optional `customComposition` array; passing `null` falls back to the preset table.
- **Narrator mode**: Host is flagged `isNarrator: true` on their player object and excluded from role assignment, win-condition checks, vote eligibility, and the night-action bot-target pool. The narrator skips `RoleRevealScreen` and goes straight to `NightPhaseScreen`. At night they see `NarratorNightDashboard` (full role visibility, submitted actions, manual Next/Skip to advance sub-phases — no auto-timer). At day they see `NarratorDayDashboard` (per-voter live breakdown, tally bars, Close Votes button) and see all roles in the player list. `useGameState` exposes `gs.isNarrator`. The day discussion timer is hidden in narrator mode; `closeVoting()` (sets `votesClosed: true`) is the narrator's trigger to end voting, which then flows into the normal `resolveLynch` path.
- **Elimination screen**: A player killed during the night sees an overlay on NightPhaseScreen with a message chosen from `nightDeathCauses[playerId]` (`DEATH_MESSAGES`), then continues to the day as a ghost.
- **Timers**: Enforced client-side only. `phaseStartedAt` stored as ISO string for reference. Host auto-submits on expire. Night steps get 45s (`SUBPHASE_TIMER`, used by wolves on later nights and the Witch); Seer and Saviour 30s, Thief and Cupid 15s (`SUBPHASE_TIMER_OVERRIDES`), and wolves on night 1 (observe only, no kill) 15s — see `subPhaseSeconds()`. Day: discussion 240s, Hunter's shot 20s (`HUNTER_SHOT_SECONDS`), lynch result screen 8s (`LynchResultModal` `DISPLAY_SECONDS`). Timers are maximums: a step ends as soon as its player acts.
- **Image assets**: Originals live in `assets-src/` as full-resolution PNGs; the app only references WebP files in `assets/`. To add or update an image, put the PNG in `assets-src/`, then export a WebP to the same path under `assets/` (quality ~85, keep alpha), sized to ~3× its on-screen size: icons 384px, small buttons 512–600px, banners 900–1320px, role cards 1200px tall, backgrounds at original size. Never `require()` from `assets-src/` — Metro would bundle the full-size file.
- **Role card images**: `RoleCard` component maps role keys to static `require()` calls for WebPs in `assets/roles/`. Roles without an image (none currently) fall back to the emoji defined in `ROLE_DEFINITIONS`.
- **Launch screen**: `LaunchScreen` is the stack's `initialRouteName`. The whole screen is a `Pressable` (no button; a "Tap anywhere to begin" hint sits at the bottom, and a ref ignores double taps). On press it loads the profile and calls `navigation.replace('Welcome')` (no saved name) or `navigation.replace('Home')`, so the back button can never return to it.
- **Player name**: entered once on `WelcomeScreen` and stored in the profile (`utils/profile.js`); Home uses it for create/join and shows "Playing as". It's changed only in `SettingsPanel` and applies to rooms created/joined afterwards — a room keeps the name the player had when they joined (`players[].nickname`), and Rejoin uses the name stored in the session. Rules: trimmed, 2–18 characters (`nicknameError`). Joining is refused if another player in the room has the same name, case-insensitive (`sameNickname`); players already in the room are exempt.
- **Join by QR code**: the Lobby shows only the letter code by default, with two buttons: Share (system share sheet) and Show QR, which opens a pop-up with a 260px `RoomQrCode` of `roomJoinLink(code)` (any player can open it; tap anywhere to close). Home's Scan QR Code opens `QrScannerModal`; a valid scan goes through the same `joinByCode()` as the typed code (room exists, still in lobby, duplicate-name check, `forgetRoomSnapshot`). The `werewolves://` scheme is not registered with the OS (no deep linking yet) — it only marks our QR codes.
- **No comments in code**: Code is self-documenting via naming.
- **Theme switching**: Day = warm oranges/cream (`DAY` in theme.js). Night = deep blues/purples (`NIGHT`). Each screen imports the correct theme constant directly and passes it to the `Timer` component.
- **Full-screen backgrounds**: `DayPhaseScreen` and `NightPhaseScreen` use `<ImageBackground>` as the root element with `resizeMode="cover"` to bleed edge-to-edge. `<SafeAreaView>` is nested inside. The header is a semi-transparent `<View>` (not an ImageBackground).
- **Phase screen header pattern**: Both phase screens use a `flexDirection: 'row'` `<View>` header containing: a pill-shaped phase badge (label + number), a centered flex-1 title, and a fixed-width timer slot. Day header: `rgba(255,245,230,0.95)` bg; night header: `rgba(13,8,32,0.82)` bg.
- **Phase screen bottom bar**: Every other button sits in a bottom bar of equal-width image buttons (`flex: 1`, image 70px tall), background `theme.glassToolbar`. Day: Leave, Notes, Day Chat, Wolf Chat (narrator only), Confirm Vote. Night: Leave, Notes, Wolf Chat (`night_chat.webp`; werewolves and the narrator only — `WerewolfAction` and `NarratorNightDashboard` no longer have their own chat buttons).
- **Glass-card pattern**: UI sections (vote panel, hunter box, player list, action boxes) use semi-transparent `rgba(...)` backgrounds so the background image remains visible. Day cards use warm cream `rgba(255,245,230,0.93)`; night action boxes use dark `rgba(10,5,28,0.78)`.
- **PhaseTransition banners**: `PhaseTransition.js` shows `dawn_banner.webp` (day) or `night_banner.webp` (night) instead of emojis, animated with Reanimated scale + fade via an `Animated.View` wrapper.
- **Image-only buttons**: All interactive buttons in phase screens are `<TouchableOpacity>` wrapping a `<Image>` WebP — no text labels. Text buttons remain only for in-game submit actions (e.g. "Confirm Kill", "Reveal Their Nature").
- **Phase counter 2-line format**: The phase counter in both DayPhaseScreen and NightPhaseScreen is split across two `<Text>` elements — `phaseLabel` (caption style, uppercase, letter-spaced) on line 1, and `phaseNumber` (fontSize: 22, fontWeight: '700') on line 2. Both sit inside the `phaseBadge` pill View in the header row.
- **Dead player row pattern**: In DayPhaseScreen, dead player rows use `backgroundColor: 'rgba(60,30,60,0.72)'` and a purple border. A purple-toned theme override is passed inline to PlayerCard (`text: '#F0ECFF'`, etc.). `noDeadOpacity` is set to prevent the 0.45 opacity from washing out the already-light text.
- **Player row pattern**: Player lists (day screen, night action components, HunterSection) use a plain `<View>` with a themed `backgroundColor` and `borderWidth: 2` `borderColor` that changes on selection. Day alive: `rgba(255,245,230,0.92)`; night: `rgba(20,10,50,0.82)`.
- **PlayerCard avatar slots**: `avatarIcon` prop takes full precedence over the letter-circle and dead-role-icon fallbacks. Day screen passes `unknown.webp` for alive players and `dead.webp` for dead players (56×56); role is already shown below the name for dead players so the role icon is not used in the avatar slot. NotesPanel follows the same logic. `avatarIconSize` defaults to 40; both screens set it to 56.
- **NotesPanel player board**: Each player gets a card (`boardCard`) with avatar + name on top and a horizontal suspicion strip below (4 level icons: innocent/neutral/suspicious/very_suspicious). Tapping an icon sets that level directly via `setSuspicion`. Dead player cards hide the suspicion strip and show an "Eliminated" label. The role picker button (top-right of each card) opens a modal with all role options; shows the role icon + name label when set.
- **Visual style**: Stained-glass medieval fantasy aesthetic consistent across all assets. Dark stone frames, jewel-toned panels, castle motifs. UI chrome (cards, overlays) should blend with this palette.

## Firebase Setup (Required Before Running)

1. Go to [Firebase Console](https://console.firebase.google.com)
2. Create a new project
3. Enable **Anonymous Authentication** (Build → Authentication → Sign-in method)
4. Create a **Firestore Database** (Build → Firestore Database)
5. Copy your web app config into `app/firebase/config.js`
6. Deploy `firestore.rules`: `firebase deploy --only firestore:rules` (project in `.firebaserc`)

### Firestore rules (`firestore.rules`)
Writes are limited to what the app does; anything else is denied:
- **Create**: only as host (`hostId == uid`, `memberIds == [uid]`, status `lobby`, one player = you).
- **Read rooms**: any signed-in user (join-by-code must find the room before you're a member).
- **Join**: a non-member in a lobby room appends only themselves to `players` (with `isHost: false`) and to `memberIds`.
- **Members**: leave the lobby / toggle own `isReady` (checked with `players.removeAll()` diffs); write only their role's `nightActions` keys while `status == 'night'`; write only `votes.<uid>` while `status == 'day'`; add/remove only themselves in `disconnectedPlayers`; take over `hostId` only for themselves.
- **Hunter**: while `hunterTriggered == uid`, may write `players`, `winner`, `status`, `hunterTriggered`, `events` (`hunterShoot` runs on the Hunter's phone, not the host's).
- **Host**: anything except `code`, `createdAt`, `hostId`, `memberIds`.
- **Chats**: members read; post as themselves, 1–500 chars (`CHAT_MESSAGE_MAX`), `createdAt == request.time`; only werewolves post in `werewolfChat`; only the host deletes.
- **When a new write path is added to the app, add a rule and a test in `firestore-tests/rooms.rules-test.js`** — otherwise it will be denied in production.
- Deploying these rules breaks app versions older than the `memberIds` change (they create/join rooms without it), so deploy only once every player has the new build.

## Tests
```bash

```
- Jest 29 with the `jest-expo` preset; config in `package.json` (`testMatch: **/*.test.js`, so helpers in `__tests__/` aren't run as tests).
- Tests live in `app/game-logic/__tests__/` and cover `roles.js`, `voteManager.js` and `gameManager.js`. `helpers.js` has `makeGame(roleByPlayer, { dead, phase, ...overrides })` (player ids double as names, in seating order), `votesFor()`, `lastUpdate(updateRoom)`, `eventsOf(update)`, `countRoles()`.
- Each test file mocks `../../firebase/roomService` (only the functions it needs) and `firebase/firestore`'s `arrayUnion` as `{ arrayUnion: items }`; assertions check the object passed to the last `updateRoom` call. `startGame.test.js` mocks `devConfig` with a mutable `BOT_CONFIG`.
- Don't assert exact `ROLE_COMPOSITIONS` rows — compare against `getCompositionForCount(n)` so the table can change.
- Run `npm test` after any change to game logic; add a test when fixing a rules bug.
- **Firestore rules tests**: `npm run test:rules` runs `firestore-tests/rooms.rules-test.js` (named `*.rules-test.js` so `npm test` skips it; config `jest.rules.config.js`, node environment) inside `firebase emulators:exec` with project `demo-werewolves`. Needs Java 21+ for the emulator, while the Android build uses JDK 17 — set `JAVA_HOME` to a JDK 21 just for that command. Run it after any change to `firestore.rules` or to how `roomService.js` writes.

## Building an Android APK (local, Windows)
```bash
cd android
./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a
```
- Output: `android/app/build/outputs/apk/release/app-release.apk`
- **CMake**: the default CMake 3.22.1 fails with `ninja: error: manifest 'build.ninja' still dirty after 100 tries`. Install CMake 3.31.6 via sdkmanager and pin it in `android/local.properties` (`cmake.dir=...\\cmake\\3.31.6`, plus `sdk.dir`). That file is per-machine and git-ignored, and `expo prebuild` deletes it — re-create it after every prebuild.
- **Release signing**: `plugins/withReleaseSigning.js` injects a `release` signingConfig on every prebuild. It reads `WEREWOLVES_UPLOAD_STORE_FILE`, `WEREWOLVES_UPLOAD_KEY_ALIAS`, `WEREWOLVES_UPLOAD_STORE_PASSWORD`, `WEREWOLVES_UPLOAD_KEY_PASSWORD` from `~/.gradle/gradle.properties` (outside the repo) and falls back to the debug key if they're missing. Never commit the keystore or its passwords.
- **Versioning**: bump `expo.version` and `expo.android.versionCode` in `app.json`, run prebuild, build, then tag `vX.Y.Z` (annotated) and push the tag. `v1.0.0` is the first tag.

## Known Limitations / Future Work
- Timers are client-side only — drifts possible on slow devices
- No server-side role secrecy: the roles map is in the room document, which every signed-in user can read; rules can't hide part of a document
- Host takeover staleness (25s) is enforced only by the app, not by the rules
- Bot support is dev/testing only — keep `BOT_CONFIG.enabled` false in shipped builds
- Disconnected players are eliminated at the end of the phase they left in (no multi-phase grace period)
- Host failover needs every player on a version with `useHostFailover`; an older host never sends heartbeats and would be replaced after ~25s
- If the host's phone dies mid-`resolveNight`, the new host re-runs it, which can duplicate some event-log lines
- **Seat selection**: Bear Tamer neighbors are determined by join order. A future enhancement could let players drag-reorder their seats in the lobby before game start, which would make the Bear Tamer's information more meaningful and closer to the physical game experience.
- Not yet implemented roles with existing artwork in `assets-src/roles/`: White Wolf, Wolf Hound
